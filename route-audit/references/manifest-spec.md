# `routes.manifest.yaml` — the contract

Everything else in this skill derives from this file. It lives at the repo root (or
`docs/audit/routes/routes.manifest.yaml`) and is **committed**.

Two halves, and keeping them separate is the whole discipline:

- **Mechanical** — `path`, `fixtures`, `auth`, `phase`. Generated by `scripts/build-route-manifest.mjs`
  from the real router. Safe to regenerate.
- **Authored** — `must_render`, `must_not`, `notes`. Written by a human (or an agent working from spec
  docs) and reviewed. **The generator never overwrites these.** A contract the agent rewrites when it
  fails is not a contract; it is a mirror.

## Schema

```yaml
meta:
  base_url: http://localhost:5173      # recorded per session in STATE, not authoritative here
  router_source: src/App.tsx           # where routes are declared — verify for this repo
  generated_at: 2026-08-07T00:00:00Z

routes:
  - path: /themes/:slug                # as declared by the router
    fixtures:                          # concrete URLs to actually visit
      - /themes/apest
      - /themes/communitas
    auth: public                       # public | required | admin
    phase: 2-themes                    # groups routes into a walk phase and a spec file
    must_render:                       # every entry becomes one Playwright assertion
      - selector: '[data-section="hero"]'
      - selector: '[data-section="cases"]'
        min_count: 2                   # plural cases — required by the canonical spec
      - selector: '[data-section="ai-lab"]'
      - selector: '[data-section="distortions"]'
      - selector: '[data-section="next-step"]'
      - text: 'Overview'               # visible-text assertion when no stable selector exists
    must_not:
      - console_errors                 # any console.error during load
      - network_failures               # any request returning >= 400
      - text: 'Lorem ipsum'
      - text: 'undefined'
    notes: >-
      Canonical twelve-section pathway page. The four load-bearing sections (plural cases,
      bound AI Lab, distortion warnings, one concrete next step) are required or the page
      fails audit.
```

## Authoring rules

**Assert structure, not prose.** `[data-section="cases"]` survives a copy edit; `text: "Three case
studies"` does not. Where the app lacks stable hooks, adding `data-section` attributes is a legitimate
part of the audit — it makes the page permanently checkable. Do this in the repair step, not mid-walk.

**Assert only what the spec requires.** Every assertion is a future failure someone has to triage.
Optional components stay out. If the canonical page spec marks a section required, it belongs here; if
it marks it optional, it does not.

**Fixtures must be seeded and stable.** A fixture pointing at a slug someone might delete will fail at
2am for the wrong reason. Prefer seeded demo content; record in `notes` where the fixture comes from.

**Phases are zones, 12–15 routes each.** Suggested for the studio: `1-public`, `2-themes`, `3-library`,
`4-formation`, `5-about`, `6-admin`, `7-dashboard`, `auth` (signed-out pass). Adjust to the repo's
actual shape; the number matters more than the naming.

**`must_not: console_errors` is stricter than it sounds.** Most apps have ambient console noise on
first run. Do not silence the rule — fix the noise, or add a narrowly scoped `ignore` list with a
written reason. A blanket exemption defeats the most valuable single assertion in the file.

## Building it for this repo

> **Verify-before-use.** The studio (ZenWrite) is a Vite + React app, so routes are **not** a
> filesystem glob — they are declared in a React Router config, likely `src/App.tsx` or a dedicated
> routes module, and there is an Express server under `server/` with its own API routes. Confirm the
> router source before generating. Existing Playwright assets live under `e2e/` (e.g.
> `e2e/api/route-coverage.spec.ts`) — reuse that setup rather than standing up a second harness.

The generator parses route declarations and merges. First run produces a manifest with every route
present and `must_render: []` — that is expected. The authoring pass fills the assertions, working
from the repo's own page/component spec docs where they exist.

Order of authority when they disagree: **the router is what exists; the spec doc is what should
exist; the manifest records the second and the audit measures the first against it.** A route in the
router but absent from the spec doc is a finding, not a manifest bug — record it, do not quietly
legitimise it.
